# 代码双轴审查指南 (Code Review)

本技能用于对当前代码库在 `HEAD` 与用户指定的**基准点**之间的 Diff 变更进行**双轴独立审查**：

- **规范轴 (Standards)**：代码是否符合项目编码规范？是否存在 Fowler 经典代码坏味道（Code Smells）？
- **需求轴 (Spec)**：代码是否完整、忠实地实现了原始 Issue / Spec 需求？是否存在功能缺失或范围蔓延（Scope Creep）？

两个审查维度通过 Antigravity 的**并行子代理 (`invoke_subagent`)** 独立执行，避免上下文污染与思维干扰，最后由主代理汇总结果并以中文清晰呈现。

---

## 核心执行原则

1. **全程中文输出**：所有审查反馈、分析说明及最终报告必须使用清晰专业的简体中文。
2. **双轴独立汇报**：严禁合并或混淆两个维度的发现。一个变更完全可能在规范上满分但在需求上实现错误（或反之），必须分开列出。
3. **前置基准校验**：在启动子代理前必须确认基准点有效且 Diff 非空，避免无谓的代理调用。

---

## 审查执行流程

### 步骤 1：锁定审查基准点 (Pin the Fixed Point)
1. 获取用户提供的基准点（如 Commit SHA、分支名、Tag、`main`、`HEAD~5` 等）。若用户未指定，主动询问。
2. 验证基准点有效性：
   ```bash
   git rev-parse <fixed-point>
   ```
3. 提取 Diff 与提交历史：
   - Diff 命令：`git diff <fixed-point>...HEAD`（使用三点语法比较 merge-base）
   - 提交清单：`git log <fixed-point>..HEAD --oneline`
4. 确认 Diff 内容非空。若为空或引用无效，在此步骤立即提示用户，终止流程。

### 步骤 2：识别需求/规格来源 (Identify Spec Source)
按以下优先级寻找原始需求定义：
1. **Commit 提交信息**中的 Issue 关联（如 `#123`、`Closes #45`、GitLab `!67` 等）。
2. **用户参数**中直接传入的文件路径或需求描述。
3. 项目内 `docs/`、`specs/`、`document/` 或 `.scratch/` 目录下与分支名/功能匹配的规格说明文件。
4. 若均未找到，向用户询问需求来源；若用户表示没有专门 Spec，则需求轴子代理将标记“无可用 Spec”并跳过比对。

### 步骤 3：识别规范来源与坏味道基准 (Identify Standards Sources)
1. **项目既有规范**：检查根目录或 `docs/` 下的编码标准（如 `CODING_STANDARDS.md`、`CONTRIBUTING.md`、开发规范文档等）。
2. **Fowler 代码坏味道基准 (Smell Baseline)**：当项目无显式规范或作为补充参考时，严格对照以下 12 种典型代码坏味道进行检查：
   - **神秘命名 (Mysterious Name)**：函数、变量、类型命名含糊，无法体现其真实用途 $\rightarrow$ 重命名并消除歧义。
   - **重复代码 (Duplicated Code)**：相同或高度相似的逻辑重复出现在多个文件/代码块中 $\rightarrow$ 提炼公共函数/模块。
   - **依恋情结 (Feature Envy)**：某个方法过多访问其他对象的数据而非自身数据 $\rightarrow$ 将方法迁移至所依赖的数据对象中。
   - **数据泥团 (Data Clumps)**：相同的若干字段或参数总是一起出现 $\rightarrow$ 封装为独立的结构体/类型对象。
   - **基本类型偏执 (Primitive Obsession)**：使用基础数据类型（如字符串、数字）代替具有特定业务含义的领域类型 $\rightarrow$ 引入领域值对象/小型类型。
   - **重复的 switch/分支 (Repeated Switches)**：相同的 `switch` 或 `if-else` 级联在多处重复判断类型 $\rightarrow$ 使用多态或统一映射表替代。
   - **霰弹式修改 (Shotgun Surgery)**：一个逻辑变更加导致在大量分散的文件中做细微修改 $\rightarrow$ 将紧密相关的内容内聚到一个模块中。
   - **发散式变化 (Divergent Change)**：一个模块因多种互不相关的业务原因而被频繁修改 $\rightarrow$ 按单一职责拆分模块。
   - **夸夸其谈未来性 (Speculative Generality)**：添加了当前需求并不需要的复杂抽象、冗余参数或钩子 $\rightarrow$ 果断删除，保持代码简约（YAGNI）。
   - **过长消息链 (Message Chains)**：形如 `a.b().c().d()` 的过长调用链 $\rightarrow$ 通过首个对象封装隐藏调用路径。
   - **中间人 (Middle Man)**：某个类或函数绝大部分工作只是单纯转发给其他对象 $\rightarrow$ 移除中间人，直接调用目标对象。
   - **被拒绝的遗赠 (Refused Bequest)**：子类继承了父类但忽略或重写了绝大部分方法 $\rightarrow$ 放弃继承，改用组合（Composition）。

> **裁决原则**：项目既有的明确规范优先级最高（若项目规范明确允许某种写法，则不视为坏味道）；跳过已由 linter / compiler 自动强制拦截的基础格式问题。

### 步骤 4：并行启动双子代理审查 (Spawn Both Sub-agents)
使用 `invoke_subagent` 工具同时启动两个子代理：

1. **规范子代理 (Standards Sub-agent)**：
   - 注入完整 Diff、Commit 清单、项目规范文档内容及上述 12 种坏味道基准。
   - 任务要求：按文件/代码块逐项报告 (a) 违反项目明确规范之处；(b) 触发的坏味道基准（标明坏味道名称、引用代码块与改进建议）。限制在 500 字以内。

2. **需求子代理 (Spec Sub-agent)**：
   - 注入 Diff、Commit 清单及提取到的 Spec 需求内容。
   - 任务要求：报告 (a) Spec 要求但缺失或实现不完整的功能；(b) Diff 中超出 Spec 要求的非预期变更（范围蔓延）；(c) 虽已实现但逻辑明显有误或与需求冲突之处。限制在 500 字以内。

### 步骤 5：汇总结算与中文呈现 (Aggregate)
将两个子代理的审查结果汇总呈现给用户，保持两轴独立：

```markdown
# 代码双轴审查报告

**审查范围**：`git diff <fixed-point>...HEAD` | **提交数量**：X commits

---

## 1. 规范审查报告 (Standards)
[展示规范子代理的完整审查结果，区分明确违规与坏味道建议]

---

## 2. 需求一致性审查报告 (Spec)
[展示需求子代理的审查结果，对照 Spec 逐条列出缺失项、范围蔓延或逻辑偏差]

---

## 3. 综合审查小结
- **规范轴**：共发现 X 处问题（其中最核心需改进项为：...）
- **需求轴**：共发现 Y 处问题（其中最核心需改进项为：...）
```

---

## 为什么坚持双轴审查

- **规范通过，需求失败**：代码写得非常优美、测试完备，但做错了功能。
- **需求通过，规范失败**：功能完全满足需求，但代码结构混乱、破坏架构规范。

分开汇报能够避免两者相互掩盖，帮助开发者和团队做出最准确的代码质量判断。
