# Git 冲突解决指南 (Resolving Merge Conflicts)

本技能指导 Agent 在遇到 Git `merge` 或 `rebase` 冲突时，系统化、安全地分析并解决冲突，保证代码质量与意图完整性。

## 核心原则

- **全程中文输出**：向用户汇报分析过程、冲突决策及验证结果时必须使用中文。
- **保留双方意图**：尽可能同时保留传入分支（Incoming）与当前分支（Current）的修改意图。
- **绝不随意放弃**：除非用户明确要求，否则不要执行 `git merge --abort` 或 `git rebase --abort`。
- **严禁臆造代码**：不要在解决冲突时引入与两方意图无关的新功能或未经讨论的代码。
- **验证驱动**：解决冲突后必须执行项目既有的自动化检查（类型检查、单元测试、代码检查）。

## 解决冲突标准流程

### 步骤 1：检查冲突现状
1. 运行 `git status` 确认当前处于 `MERGING` 还是 `REBASING` 状态，并列出所有处于冲突状态的文件（Unmerged paths）。
2. 查看冲突提交历史，确认合并的目标分支与源分支：
   ```bash
   git log --oneline -n 5
   ```

### 步骤 2：溯源各方修改意图
1. 深入分析每个冲突文件的两端修改：
   - 检查提交信息（Commit messages）、关联的 PR、Issue 或任务描述。
   - 区分“哪边做了什么”以及“为什么做”。
2. 查看冲突标记（`<<<<<<<`, `=======`, `>>>>>>>`）及其上下文。

### 步骤 3：逐块合并与解决
1. 逐个文件、逐个代码块进行处理：
   - 若两方修改为互补逻辑（如分别添加了不同的方法或导入），合并两方变更并理顺次序。
   - 若两方修改产生逻辑冲突，优先选择符合当前合并/变基目标的一方，并在解释中说明权衡考量。
2. 移除所有冲突标记符号，保持代码语法完整。

### 步骤 4：自动化校验与修复
1. 识别项目中的构建与验证命令（根据 `package.json`、`pyproject.toml`、`Makefile` 等）：
   - 类型检查（Typecheck，如 `tsc --noEmit`、`mypy`）
   - 单元测试（Tests，如 `npm test`、`pytest`）
   - 代码检查与格式化（Lint/Format）
2. 运行自动化检查，修复因合并引入的编译报错、类型不兼容或测试失败。

### 步骤 5：完成合并或继续变基
1. 暂存所有已解决并验证通过的文件：
   ```bash
   git add <resolved-files>
   ```
2. 根据当前操作类型完成流程：
   - **Merge 操作**：完成提交 `git commit`（或保持自动生成的 merge commit 信息）。
   - **Rebase 操作**：执行 `git rebase --continue`，若后续 commit 仍有冲突，重复上述步骤直至整个 rebase 序列全部完成。
3. 用中文向用户总结冲突原因、解决策略及自动化验证结果。
