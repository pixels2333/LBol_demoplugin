# 变更提案: 内联单次调用私有方法（反过度抽象重构）

## 元信息
```yaml
类型: 重构
方案类型: implementation
优先级: P1
状态: 草稿
创建: 2026-05-07
```

---

## 1. 需求

### 背景
networkplugin 项目（~62,000 行，179 个 .cs 文件）中存在大量"为了抽象而抽象"的过度封装：私有方法仅被项目内 1 处调用，却单独抽离为命名方法。这导致阅读代码需要频繁跳转、打断流程理解。经探查，仅 TradePanel.cs（4,712 行）中就有 39 个单次调用私有方法，工厂类中另有 16 个，合计已知 55+ 处。

### 目标
将项目中所有**仅被 1 处调用且方法体 ≤50 行**的私有方法内联到唯一调用点，消除不必要的间接层，减少代码行数 800-1500 行，提升代码可读性。

### 约束条件
```yaml
兼容性约束: 不得改变任何运行时行为（纯等价变换）
安全约束: HarmonyX Patch 方法、Unity 生命周期方法、public/internal 方法一律不动
构建约束: 每完成一个文件须 dotnet build 验证，0 error 硬性门槛
```

### 验收标准
- [ ] 所有目标文件中的单次调用私有方法（≤50 行）已内联
- [ ] 所有目标文件的 dotnet build 均通过（0 error）
- [ ] 无运行时行为变更
- [ ] 代码总行数减少 ≥500 行

---

## 2. 方案

### 技术方案
逐文件扫描 → 识别仅 1 处调用的私有方法（grep 验证跨文件）→ 按方法体行数分级：
- **P0（≤15 行）**：直接内联，无脑执行
- **P1（16-50 行）**：评估后内联
- **P2（51-100 行）**：人工决策，部分保留
- **P3（>100 行）**：保留不内联

内联方式：将方法体代码直接替换到唯一的调用点，删除原方法声明。内联后若调用者过长（>100 行）也接受。

### 影响范围
```yaml
涉及模块:
  - UI/Panels/TradePanel.cs: 39 个单次调用方法，预计内联 ~25 个（≤50 行）
  - UI/Panels/ResurrectPanel.cs: 待探查
  - UI/Dialogs/TradeDetailDialog.cs: 待探查
  - UI/Factories/（6 文件）: 16 个单次调用方法，预计内联 ~14 个
  - Patch/UI/OtherPlayersOverlayPatch.cs: 待探查
  - Patch/UI/MainMenuMultiplayerEntryPatch.cs: 待探查
  - Patch/UI/GapOptionsPanel_Patch.cs: 待探查
  - Patch/Network/EventSyncPatch.cs: 待探查
预计变更文件: ~12 个
```

### 风险评估
| 风险 | 等级 | 应对 |
|------|------|------|
| 内联后变量名冲突 | 低 | 替换时检查同名局部变量，必要时重命名 |
| 内联后编译失败 | 低 | 每个文件完成后立即 dotnet build 验证 |
| 100+ 行方法过载 | 低 | P2/P3 方法不内联，避免调用者膨胀 |
| 误删多调用方法 | 低 | 内联前 grep 全项目确认仅 1 处引用 |
